# Additional PowerPoint parser candidates

The latest [eight-parser report](../output/pptx-benchmark-20261106/report/peers/index.html) measures duke-pptx, Office Oxide 0.1.16, undoc 0.27.3, python-pptx 1.0.2, MarkItDown 0.1.9, pptxboss-core 2.3.0, BetterOffice 0.5.1 and rustypptx 0.2.0. The latter three have pinned adapters, a 43-input feature-bearing pilot and a fresh 630-input comparison. All 628 reference-bearing inputs remain in accuracy denominators; 610 nonempty inputs form the common timing cohort. The separate legacy agreement study uses Apache POI 6.0.0 as an independent reference. The fourth additional candidate, pptx 0.1.0, remains researched but unmeasured.

| Candidate | Relevant public API | Comparison requirements |
| --- | --- | --- |
| [pptxboss-core 2.3.0](https://docs.rs/pptxboss-core/latest/pptxboss_core/document/struct.Document.html) | In-memory document loading, per-slide parsing, notes, comments, charts, diagrams and image resources; OOXML and legacy PPT | Opening the document is lazy. Time materialization of the required slide content and assets; report single-thread and parallel configurations separately. Retain reported skipped content as a coverage failure rather than silently excluding that input. |
| [betteroffice-pptx-parse 0.5.1](https://docs.rs/betteroffice-pptx-parse/0.5.1/pptx_parse/) | Typed presentation, slides, layouts, masters, charts, tables, pictures, media, source-shape records and bounded parsing | Its structured package model is a closer comparison to the renderer-facing Rust contract. Keep parsed properties separate from raw retained package parts; copying a part does not prove typed or visual support. |
| [rustypptx 0.2.0](https://docs.rs/rustypptx/0.2.0/rustypptx/) | Path-based and byte-based parsing to structured content | Use the byte API to match input-I/O treatment. Inspect which outputs and image bytes are materialized, and record its parallelism before comparing latency. |
| [pptx 0.1.0](https://github.com/hidemi-ito/duke-pptx/blob/main/Cargo.toml) | `Presentation::open`, followed by slide XML access and `ShapeTree::from_slide_xml`; a read/write library with tables, charts, media and animation APIs | Opening the package alone is insufficient. Time parsing all slide shape trees and any separately loaded content used in feature scores. Verify the read path independently of advertised writing features, and pin the release or source commit before measurement. |

This is not an exhaustive list of existing parsers, and API availability is not proof of accurate support. Published throughput claims use different output scopes, corpora and timing methods and cannot be substituted for the local common-cohort measurement. New adapters must expose the same independently scored feature facts, preserve failures in accuracy denominators, and identify unsupported dimensions explicitly.


The [adapter implementation and method](../scripts/pptx-benchmark/peers/README.md) include lazy-content materialization, fixed thread counts, actual decoded media hashing, retained partial-output diagnostics and explicit unscored dimensions. The new source-feature results expose sparse-chart cache gaps and text-versus-raster compatibility choices. The current Rust parser has stronger literal body-text recall but remains slower than several peers; pptxboss has higher macro text F1. No overall accuracy or speed victory is claimed.
